# TC 규격의 근거 — 세 세션 실측 종합

출처: `catalog-ppt-tc-case`(TC 150건 작성 경험) / `universe-harness`(정적 게이트 하네스) / `harness-01`(Playwright 실전)
정리: 2026-09-07

---

## 0. 세 저장소 모두 "TC 티켓 → Playwright" 파이프라인은 없었다

| 세션 | 실제로 가진 것 | 우리에게 옮겨올 것 |
|---|---|---|
| `catalog-ppt-tc-case` | 수기 TC 150건 (xlsx 5시트) | TC 분해 기준, 컬럼 축 |
| `universe-harness` | 코드생성 + 정적 관문 (Playwright 없음) | "못 쟀다" 규율, 자기 채점 방지 |
| `harness-01` | Playwright e2e 13파일 (TC 문서 없음) | 거짓 통과 4종, 사전조건 필드 |

세 곳 다 절반씩만 가지고 있다. 우리가 만드는 게 그 사이를 잇는 첫 시도라고 봐야 한다.

## 1. 데인 것은 전부 "틀린 답"이 아니라 "아무것도 안 잰 초록"이었다

### 거짓 통과 4종 (`harness-01` 실측)

**① 없는 라우트를 재고 PASS**
- `/findInfo`를 쟀으나 실제 경로는 `/member/findInfo`
- `/member/join`을 쟀으나 실제는 `/join`
- **404 페이지는 본문 65자·입력 0개·버튼 1개라 "위반 0건"으로 읽힌다.**
  가드 도입 후 같은 화면 실측: 입력 18개·버튼 6개.

→ 규격 반영: **화면을 경로 문자열이 아니라 이름으로 참조.** 이름이 틀리면 즉시 throw.

**② 요소 0개를 "위반 없음"으로 읽음**
```js
if (count < min) throw new Error(
  `측정 대상이 ${count}개다. 0개는 "위반 없음"이 아니라 미도달·셀렉터 오류 신호다.`);
```
→ 규격 반영: **기대 모수 필드.**

**③ 하한·fallback에서의 우연한 일치**
- 도넛 QA가 `canvas 220 / wrap 220`으로 PASS를 냈으나 `min-h` 하한에 앉은 일치였다.
- 더 무서운 얼굴: **"CSS 변수 == 실측 높이"는 fallback이 같은 식을 옮긴 것이라
  JS가 한 번도 안 돌아도 성립한다.**

→ 규격 반영: **하한이 아닌 입력값 필드.** "A가 B를 따라간다" 명제 전용.

**④ 에러 경계가 크래시를 삼킴 — dev만 보면 속는다**

| 빌드 | `pageerror` | console |
|---|---|---|
| dev | 2건 | 1건 |
| 프로덕션 | **0건** | 1건 |

→ 규격 반영: **검증 대상 빌드 필드.**

### 메타 함정 — 검사기 자신이 공허해진다

- `testMatch`가 명시 정규식이라 **새 spec을 등록 안 하면 조용히 안 돈다.** 안 도는 건 실패하지 않는다.
- 한때 "실파일에 리터럴 N개 이상"으로 추출기 생존을 검사했더니,
  코드가 개선될수록 검사가 빨개지는 **뒤집힌 유인**이 생겼다. 합성 fixture로 교체.

→ CI에 넣을 것: 스캔 파일 0개면 실패 / 새 spec이 목록에 없으면 실패 / 탐지기에 크래시를 주입해 빨개지는지 확인.

## 2. "못 쟀다"를 어디에 둘 것인가 — 두 세션이 정반대로 답했다

**`universe-harness`:** 3상태로 분리하라(✅/❌/⚪). 근거 — 2상태면 안 잰 것이 통과로 세어진다.
실제 사고: 저장소가 `test` 명령을 선언 안 했는데 도구가 기본값을 지어내 돌리고
`✅ exit 0`을 찍었다. 테스트 0개인 저장소에서.

**`harness-01`:** 별도 상태를 두지 말고 Fail로 강등하라. 근거 — 별도 상태로 두면 초록으로 읽힌다.
404 도달·모수 0·하한 일치를 전부 throw로 처리.

**우리 결론 — 층위가 다르다:**
- **수기 실행 리포트**는 4상태(Pass/Fail/Block/N/A). 안 돌린 TC가 Pass로 세어지면 안 된다.
- **Playwright 스크립트 내부**는 2상태. 스크립트 안에 "못 쟀다"를 만들면 초록으로 읽힌다.

## 3. 자기 채점 방지

> 에이전트가 TC도 쓰고 스크립트도 쓰면 자기 채점이다. (`universe-harness`)

그쪽 장치: 구현 전에 테스트를 받고, **그것이 지금 빨간불인지 기계로 확인**한다.
처음부터 통과하는 테스트는 거부한다.

→ 우리 파이프라인의 같은 구멍: **TC → 스크립트 변환 직후 그 스크립트가 아직 실패하는지 확인하지 않으면,
아무것도 안 재는 스크립트가 초록으로 쌓인다.**

## 4. 자연어 명제를 단언으로 옮길 때 막히는 표현들

| 표현 | 왜 막히나 | TC에 뭘 적어야 하나 |
|---|---|---|
| "~ 제목이 보인다" | `getByRole`의 name은 **기본 substring**. "계정 정보"가 "미납 담당자 연락처 정보"와 겹침 | 정확 일치 여부 + 제목 레벨 |
| "발송 폼이 보인다" | 계정 상태에 따라 폼/제한 다이얼로그 중 하나만 보임 → 한 갈래만 적으면 다른 계정에서 플레이키 | 분기 조건과 갈래 전부 |
| "A 단계에 갈 수 없다" | 실제로는 리다이렉트. 어디로 튕기는지 안 적으면 **404로 튕겨도 통과** | 기대 착지 URL |
| "A가 B를 따라간다" | 하한·fallback·기본값에서의 일치는 증거가 아님 | 하한이 아닌 입력값 |
| "위반이 0건이다" | 모수 증명 없으면 미도달과 구별 불가 | 기대 모수 |
| "에러가 나지 않는다" | dev와 프로덕션의 신호가 다름 | 검증 대상 빌드 |
| "버튼이 비활성화된다" | `<button disabled>`가 아니라 div에 onClick이 붙고 핸들러 첫 줄에서 return인 경우가 있음 → `toBeDisabled()` 실패 (`catalog-ppt-tc-case` 실사고) | "클릭해도 요청이 발생하지 않는다"처럼 **동작**으로 |

※ 마지막 항목은 `catalog-ppt-tc-case`의 사례다. `harness-01`은 자기 저장소엔 그 함정이 없다고 명시적으로 부인했다
(`toBeDisabled()` 5건 전부 정상). 저장소마다 다르므로 **구현을 단정하지 않는 문장**이 안전하다.

## 5. 사전조건 — `beforeEach`로 바로 떨어지려면

`harness-01`이 실제로 필요로 했던 필드가 `routes.ts` 인터페이스에 그대로 있다:
`name` / `cleanContext`(인증이 있으면 안 되는 화면) / `expect404`.

**사람이 다시 해석해야 했던 것 셋:**
1. **"로그인 상태"만 적힌 것** — 로그인이 **있으면 안 되는** 화면이 있어서 2값이면 틀린다. 3값 필수.
2. **경로를 문자열로 적은 것** — `/findInfo`·`/member/join` 사고의 원인.
3. **선행 상태가 어디 사는지 안 적힌 것** — 위저드 상태가 **영속화 안 되는 인메모리 zustand**라
   `goto`마다 초기화된다. 이걸 알았으면 `beforeEach`가 불필요하다는 판단이 즉시 났을 것.
   **"가장 크게 아꼈을 항목"**이라고 자평.

## 6. TC 분해 기준 (`catalog-ppt-tc-case`, 150건 실적)

- **기능 단위로 1차 분해, 화면 단위 아님.** 한 화면에 다 들어있으면 화면으로 쪼개도 1덩어리다.
  "입력 필드 그룹 + 상태 전이"를 대분류로.
- **상태 전이는 독립 대분류로 승격.** 판단 기준: **"이 규칙이 틀리면 기능이 성립하지 않는가."**
  필드 검증은 부분 실패지만 상태 전이 규칙은 틀리면 결과물 자체가 깨진다.
- **쪼갤지 몰지: "관찰만 하면 1행, 상태가 바뀌면 N행."**
  타입별 필드 노출 매트릭스는 1건, 타입 전환 시 값 초기화는 전이 방향마다 쪼갬.
  ※ 단, 우리 규격은 **리스트 컬럼 검증을 Expected 단위로 쪼갠다**(Action 1 + Expected N).
- **경계값은 통과/실패 쌍으로.** 단 **입력 단계에서 막히면 1행, 저장 시점 검증이면 2행.**
- **에러 문구는 코드 원문 그대로** 기대결과에 박는다.
- **조합 폭발은 축을 의식적으로 갈라서** — 축소한 축과 전수 돌린 축을 명시하고, **축소 근거를 TC에 남긴다.**
- **의심 지점(ISSUE-##)도 TC화**하고 기대결과에 병기 → 실패 시 신규 버그인지 기지 이슈인지 즉시 구분.
- **기대결과 미확정 건은 `[기대]` + `※ 현 동작` 병기.**
- 커버리지 완료 조건: **모든 요구사항 ID가 최소 1건 매핑.**

## 7. Playwright 하네스 쪽 참고 사항 (`harness-01` 실측)

- **셀렉터: `getByRole` 단일 노선.** `getByTestId` 0건, `data-testid` 0건(프로덕션 코드에 없음).
  역할로 못 잡는 것은 CSS 클래스가 아니라 **ARIA 속성**으로 내려간다 (`div[aria-haspopup="dialog"]`).
- **POM 안 씀, 후회 없음.** 공통화 축이 "페이지"가 아니라 **"거짓 통과를 막는 관문"**.
  화면 개편 중에는 POM 추상화 층이 매번 같이 깨진다.
- **fixture가 이긴 자리:** spec이 `test`를 `@playwright/test`가 아니라 `./errorSignals`에서 import.
  `auto: true`라 모든 spec이 자동으로 에러 신호를 듣는다.
  **"까먹으면 안 되는 것"은 픽스처로 내린다.**
- **`waitForTimeout`:** 커밋본 5건 / 임시 스크립트 162건. 남은 5건은 전부 **기하를 재기 직전**이고
  주석이 붙어 있다. **"보인다"와 "위치가 확정됐다"는 다른 사건**이고 후자엔 auto-waiting이 없다.
- **모달:** `getByRole('dialog')`로 스코프를 잡고 그 안에서 찾은 뒤 **`toBeHidden()`으로 닫힘까지 단언.**
- **테이블:** `getByRole('columnheader', { name })` 루프.
- **retries 0** → retry가 버그를 덮은 사례 없음. 다만 `trace: 'on-first-retry'`와 모순이라
  **트레이스가 한 번도 안 남는다.** `retain-on-failure`로 가야 한다.
- **재사용될 검증 로직은 반드시 커밋되는 곳에 산다.** gitignore 안에 있어서 다음 세션에 전달이 안 됐고,
  같은 404 사고가 반복됐다.

## 8. 저장소 배치 결정 — universe-harness에 넣지 않는다

`universe-harness`에 편입 가능성을 물었고, **별도 저장소를 권고받았습니다.** 근거 4가지(전부 실측):

1. **입력이 다르다.** 그쪽은 "요구사항 한 줄 → 컴포넌트 하나", 우리는 "정책서 한 편 → TC 묶음".
   컴포넌트 하나에 매인 구조(폴더 밖은 못 씀, 하나에 계약 하나)가 안 맞는다.
2. **판정 층이 다르다.** 그쪽은 "이 컴포넌트가 저장소 안에서 서는가" — 저장소 안에서 끝난다.
   우리는 "이 정책이 지켜지는가" — **돌고 있는 앱이 있어야 한다.**
3. **CI 무게.** 현재 관문 26개 전체가 **1분**. 브라우저(~300MB) + 앱 기동이 들어오면 균형이 깨진다.
   **느려진 관문은 아무도 안 본다** — 관문을 죽이는 가장 흔한 방법.
4. **붙일 자리가 없다.** 소비 저장소 세 곳 중 진짜 프로덕션인 `backoffice`는 **유닛 테스트조차 없다.**
   안 타는 갈래를 들이면 죽은 축이 된다. 실제 전례: `typecheck` 축을 R45에 선언해놓고 **R146까지 한 번도 안 돌았다.**

⇒ **가져올 것은 규율이지 구조가 아니다.**

## 9. "구현 전 빨간불" 장치 (`bigbang/nebula.mjs`의 `runContractPhase`)

```
계약 수령 → 관문(범위·정적 규칙) 통과 → 그 테스트를 지금 돌린다
  exit === 0  → ⛔ 거부. "처음부터 통과 = 아무것도 재지 않는다". 파일 삭제
  exit !== 0  → ✅ 수용. 보호 목록에 넣어 이후 못 고치게 한다
```

세 갈래를 실주행으로 확인했다고 함: 빨간 계약 수용 / 빈 계약 거부 / 계약을 나중에 느슨하게 고치려 하면 차단.

**그 장치에서 스스로 찾은 구멍(공유받음):** 계약을 **못 받았을 때** 조용히 진행하고
게이트가 초록이면 exit 0으로 끝났다. **"재 달라고 했는데 안 재고 통과로 보였다."**
→ 고친 방식: 재시도 1회 → 그래도 못 받으면 **exit 3**(실패도 통과도 아님).

## 10. ⚪를 실패로 접을 것인가 — 두 세션의 대립과 우리 결론

**`harness-01`:** 별도 상태를 두지 말고 **Fail로 강등**하라. 별도 상태는 초록으로 읽힌다.

**`universe-harness`:** **실패로 접지 마라.** 실패로 접으면 사람이 "도구가 깨졌다"고 읽고 검사를 끈다.
실측 근거 — 소비 저장소에서 13개 중 9개가 빨간불이 되자 실제로 그렇게 됐다.
대신 **세 층 전부에 ⚪를 둔다**:

| 층 | 표현 |
|---|---|
| 신호 | `ISignal.unmeasured?: string` — `ok`는 뜻이 없다고 주석에 못 박음 |
| 판정 | `[SOLVED]`는 잰 것으로만 계산. 못 잰 축은 **따로 이름을 부름** |
| 종료코드 | `EXIT_UNMEASURED = 3` — 0도 1도 아님 |

**우리 결론:** 층위로 가른다.
- **스크립트 내부**는 throw(= `harness-01` 방식). 스크립트 안의 "못 쟀다"는 초록으로 읽힌다.
- **리포트·파이프라인**은 ⚪ 유지(= `universe-harness` 방식). 단 **집계 분모에서 뺀다.**
  "25개 중 25개 통과"에 N/A가 섞이면 그 숫자는 거짓이다.

## 11. 모델 산출물(정책서 → TC)의 검증 한계

`universe-harness`도 **여기가 제일 약한 자리**라고 인정했습니다. 낸 답:

> **"내용이 옳은가"는 안 잰다. "형식이 재고 있는가"만 잰다.** 그리고 그 둘을 **말로 갈라 적는다.**

정적으로 잡히는 것: 필수 필드 누락 / **부정 검증 0줄** / 요구사항 ID 미매핑 / Action↔Expected 번호 불일치.

⛔ 못 잡는 것: **필드가 다 채워졌지만 얕은 TC.** 그쪽도 못 잡고 "얕은 계약이 얼마나 흔한지 모른다(N=1)"로
미해결 목록에 올려뒀다고 합니다. **못 잡는다고 문서에 적는 것**이 최선이라는 게 답이었습니다.

## 12. 우리 양식에서 지적받은 구멍 4개 (v1.1에서 수정)

"채워져 있어도 아무것도 안 재고 통과할 수 있는 자리"를 짚어달라고 요청한 결과:

| # | 구멍 | 왜 | v1.1 조치 |
|---|---|---|---|
| 1 | **셀렉터 힌트** | 그 요소가 **항상 존재하면** 셀렉터가 정확해도 아무것도 안 잰다. "소진 배지가 보인다"는 배지가 늘 떠 있어도 통과 | 표에 **조건 A / 조건 B 대비 열** 추가. 조건 대비 없는 관측은 무효 |
| 2 | **부정 검증 "최소 1줄"** | 줄 수는 채워도 **약한 부정**이면 소용없다. "에러 토스트가 안 뜬다"는 아무 일도 안 일어나도 통과 | **"행동을 했는데도 일어나지 않았다"** 형태 강제. `[행동] → [일어나지 않아야 할 것]` 구조 |
| 3 | **기대 착지 URL** | URL만으로는 **404·에러 페이지도 통과**한다. harness-01의 404 사고가 정확히 이 자리 | **착지 증거 요소**(그 화면에만 있는 요소 하나) 필드 신설 |
| 4 | **인증 "무관"** | 편해 보이지만 **안 잰다는 뜻**. 무관이 많아지면 인증 분기는 영영 안 재진다 | `무관`은 ⚪로 집계, 통과 쪽에 섞지 않음을 명시 |

좋은 계약의 예로 받은 것: `remaining>0`이면 enabled, `0`이면 disabled를 **둘 다** 잰 것.
그리고 `expect(onSend).not.toHaveBeenCalled()` — **버튼을 눌렀는데도** 발송이 안 나갔다.
누르지 않고 확인하면 항상 통과한다.
