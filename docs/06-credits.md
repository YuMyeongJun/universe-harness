# 출처

> 이 우주는 무에서 만들지 않았다. **셋에서 채택했고, 각각에서 무엇을 바꿨는지 적는다.**

## 한눈에 — 무엇을 채택했고 무엇은 안 했나

| 출처 | 무엇을 | 채택한 것 | **안 가져온 것** |
|------|--------|-----------|------------------|
| **§1** EnvHarness | 규격 | 「정적 환경을 고치지 않고 밖에서 감싼다」 · `reset`/`step` 인터페이스 · Setup·Rule·Link 3부품 | **목적** — 에이전트 학습이 아니라 코드 품질에 쓴다 |
| **§2** Toss Frontend Fundamentals | 규칙 | 물질 법칙 넷의 축(네이밍·평탄성·응집·파생 state) | **기계가 셀 수 없는 축** — 판정 레인에 남기거나 뺐다(적용 범위는 7장) |
| **§3** 카카시 하네스 | 프레임 | 3층 구조 · 배포판 범위 · 로그 평가 규율 · 스키마 lint | **은유**(정원) · **검사의 깊이** — 형식만이 아니라 동작을 기계가 잰다 |

| 출처 | 라이선스 | 코드를 가져왔나 |
|------|----------|-----------------|
| EnvHarness | Apache 2.0 | ❌ **안 가져왔다.** 규격(reset/step)과 발상을 참고했다 |
| Toss Frontend Fundamentals | 공개 문서 | ❌ **문장도 안 옮겼다.** 판단 기준을 규칙으로 재구현했다 |
| 카카시 하네스 | MIT | ❌ **안 가져왔다.** 구조와 운영 규칙을 참고했다 |

세 곳 모두 **코드 복사가 아니라 설계 채택**이다. 관측 엔진(`observatory/engine`)은 자체 구현이다.

## 1. EnvHarness (Google Research) — 규격

**[google-research/envharness](https://github.com/google-research/envharness)** · Apache 2.0
논문: *EnvHarness: Awakening Static Worlds for Agent Learning*, Huang et al. (2026) · [arXiv:2608.19880](https://arxiv.org/abs/2608.19880)

### 채택한 것

**정적인 환경을 고치지 않고 밖에서 감싼다**는 발상 자체다.

> 전통적인 상호작용 환경은 정적이다 — 어떤 에이전트가 상호작용하든, 그 에이전트가
> 얼마나 나아졌든 똑같이 행동한다.

우주의 **보존 법칙**이 여기서 나왔다. 은하(저장소)의 코드를 한 줄도 고치지 않고,
그 저장소가 이미 가진 명령을 부르는 것으로만 검증한다.
그리고 `reset` / `step` 인터페이스를 관측 엔진이 그대로 따른다.

세 부품의 대응은 이렇다:

| EnvHarness | 우주 | 무엇 |
|------------|------|------|
| **Setup** — 초기 상태를 재구성 | 스테이지의 결함 주입 | 샌드박스에 결함을 심는다 |
| **Rule** — 상호작용을 재구성 | **관문(Contract)** | 에이전트의 쓰기를 파일에 닿기 전에 가로챈다 |
| **Link** — 다른 환경의 과제를 조합 | 은하 · 태양계 | 여러 저장소·기능 묶음을 같은 법칙 아래 둔다 |

### 바꾼 것 — 목적

EnvHarness 는 **에이전트 학습**을 위한 환경 프레임이다.
우주는 그 규격을 빌려 **프론트엔드 코드 품질**에 쓴다 — 학습이 목적이 아니라
**태어나는 코드가 법칙을 지키게 하는 것**이 목적이다.
그래서 `evaluate()` 자리에 게이트(lint·build·test)와 정적 규칙이 들어온다.

## 2. Toss Frontend Fundamentals — 규칙

**[frontend-fundamentals.com](https://frontend-fundamentals.com/)** · [toss/frontend-fundamentals](https://github.com/toss/frontend-fundamentals)

> 변경하기 쉬운 프론트엔드 코드를 위한 지침서

### 채택한 것

우주의 **물질 법칙 넷**이 이 지침서의 축에서 나왔다.

| 우주의 법칙 | 무엇을 본다 |
|-------------|------------|
| **네이밍** | 이름이 "무엇인지"가 아니라 "무엇을 위한 것인지"를 말하는가 |
| **평탄성** | 예외가 먼저 반환되어 본류가 평평한가 (얼리 리턴 · 중첩 삼항) |
| **응집** | 한 컴포넌트가 boolean prop 으로 여러 화면을 겸업하지 않는가 |
| **(성운)** 파생 state | props 를 state 로 복사하고 `useEffect` 로 되맞추지 않는가 |

**17패턴 중 무엇을 덮었고 무엇을 안 덮었는지는 [7장](07-toss-coverage.md)이 표로 센다.**

### 안 가져온 것

**모든 규칙을 옮기지 않았다.** 「응집이 맞는가」·「성급한 추상화인가」처럼
기계가 셀 수 없는 것은 판정 레인(LLM)에 남기거나 아예 빼뒀다.

### 바꾼 것 — **읽는 지침서를 무는 관문으로**

지침서는 사람이 읽고 판단하는 글이다. 우주는 그것을 **기계가 세는 규칙**으로 옮겼다.
그러면서 한 가지를 배웠다:

⚠️ **옮기는 순간 오탐이 생긴다.** 지침서에는 없던 문제다.
실측에서 오탐 4종·153건이 나왔고, 그중 가장 나빴던 것은 관문이
**지키라는 것을 지킨 코드를 벌하는 것**이었다(`bg-[var(--token)]` 를 「임의 값」으로).

그래서 우주에는 지침서에 없는 규칙이 하나 더 있다 —
**「법칙이 헛돌면 뺀다.」** 헛도는 관문은 무시하는 법부터 가르치기 때문이다.

## 3. 카카시 하네스 — 프레임

**[psmon/harness-kakashi](https://github.com/psmon/harness-kakashi)** · MIT

Claude Code 플러그인으로 배포되는 기획/QA 하네스. 「정원」 은유를 쓴다.

### 채택한 것

| 카카시 | 우주 |
|--------|------|
| 3층 구조(지식·에이전트·엔진) | 법칙 · 힘 · 궤도 |
| **배포판에는 기본 프레임만** — 씨앗 + 절차 | 법칙·관측소는 배달, 힘·은하는 배달 안 함 |
| 「꽃은 배달되지 않는다」 영입 5-파일 패턴 | 힘 발견 4-파일 절차 |
| 로그마다 **평가 필수** · 합성 등급 금지 · 근거 없는 등급 무효 | 그대로 |
| **「로그에만 남은 제안은 실행되지 않는다」** | 라운드 궤도 ⑤단계 (성운 승격) |
| 로그 스키마를 lint 로 집행 · 「정본은 템플릿, 스크립트는 집행자」 | `verify-laws.sh` |
| 차크라 — 토큰 경제 감사 | 성운에 후보로 등재 |

### 바꾼 것 — 은유와, 검사의 깊이

| 무엇 | 카카시 | 우주 |
|------|--------|------|
| **① 은유** | 정원 — *가꾸는* 것이라 느리게 자란다(그 저장소 실측: 첫 미션 11 라운드, 제품 하나 89일) | 우주 — *터져 나오는* 것이다. 은유가 곧 설계 철학이라 구조를 그대로 옮기지 않았다 |
| **② 검사의 깊이** | **형식**(frontmatter·필수 절)을 검사하고 **동작은 사람이 본다** | **관측소**가 있다 — 게이트와 관문으로 별이 실제로 도는지 **기계가 잰다** |
| **③ 배달 범위** | 에이전트를 배달하지 않는다(도메인에 매여 있으므로) | **법칙은 배달한다** — 프론트엔드 규칙은 도메인 무관이기 때문이다 |

**②가 핵심이다.** 나머지 둘은 취향의 차이지만, 이것은 「무엇을 증거로 삼는가」의 차이다.
