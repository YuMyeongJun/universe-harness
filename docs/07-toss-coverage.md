# 토스 17패턴 커버리지

[Toss Frontend Fundamentals](https://frontend-fundamentals.com/) 는 **4기둥 17패턴**이다.
우리는 「채택했다」고 적어 왔는데 **무엇을 채택하고 무엇을 안 했는지 세어 본 적이 없었다.**
이 표가 그 셈이다.

## 결론 먼저 — 가져오지 않고 참고한다

**가져오면 안 되는 이유가 문서 안에 있다.** 17패턴 중 「중복 코드 허용하기」는
순진한 DRY 린트와 **정반대**다. 이 문서는 규칙집이 아니라 **생각하는 법**이다.

우리 법칙은 「검사가 없는 법칙은 장식이다」이다. 17개를 그대로 들이면 **장식이 열 개 넘게
생긴다.** 그래서 참고만 하되, **참고를 정직하게** 한다 — 아래 표가 그것이다.

⚠️ 그리고 우리가 고른 방식도 정직하게 적는다. 우리는 중요도가 아니라
**정규식으로 재기 쉬운 것**을 골랐다. 그건 선택 편향이고, 표의 「기계로 잴 수 있나」 칸이
그 편향을 드러낸다.

## 셈

| | 수 |
|---|---:|
| 전체 패턴 | 17 |
| 덮음 | **4** (3 · 5 · 7 · 13 — 5와 13은 같은 규칙) |

## 우리가 잘못 붙인 이름

**「응집 법칙」은 토스의 응집도가 아니다.** `quality/cohesion`(boolean prop 3개 이상)은
토스 분류로는 **가독성**의 「로직 종류에 따라 합쳐진 함수 쪼개기」다.
이름을 그대로 두되 이 사실을 여기 적어 둔다 — 법칙 이름을 바꾸면 은하의 설정이 깨진다.

## 다음에 만들 것

「잴 수 있는데 안 한 것」 넷이 다음 후보다. 어려운 순으로:

1. ~~복잡한 조건에 이름 붙이기~~ — **만들지 않기로 했다.** 잴 대상이 없어 검증을 못 한다(위 표 4번)
2. **Props Drilling** — 같은 prop 이름의 전달 깊이
3. ~~이름 겹치지 않게~~ — **한 번 재서 복제 넷을 걷어냈다.** 다만 규칙으로는 안 만들었다 — 저장소 전체를 봐야 해서 파일 단위 관문에 안 맞는다
4. **함께 수정되는 파일** — git 이력이 필요하다. 정적 훑개가 아니라 **이력 훑개**다

## 매직 넘버 규칙을 만들며 배운 것

이 라운드에서 실제로 만든 것은 하나(`quality/magic-number`)인데, **작은 표본에서
12/12 통과한 뒤 엔진 소스 52파일에 걸자 오탐이 세 종류 나왔다:**

| 오탐 | 왜 |
|---|---|
| 정규식 리터럴의 수량자 `/…{200,}/` | 훑개가 정규식을 코드로 봤다 |
| 템플릿 문자열 속 픽스처 코드 | `` `useState(180)` `` 을 진짜 코드로 봤다 |
| HTTP 상태 코드 `status === 404` | **숫자 자체가 이름**이라 이름을 붙이면 나빠진다 |
| 데이터 레코드의 값 `price: 4500` | 매직 넘버는 **로직을 정하는 수**이지 레코드의 값이 아니다 |

넷 다 **작은 표본에는 없었다.** 규모에서 재고 49 → 34 → **32** 로 줄인 뒤에야 쓸 만해졌다.
마지막 것(데이터 레코드)은 **엔진이 아니라 픽스처 은하**에 걸어 보고서야 보였다 —
말뭉치를 하나만 보면 그 말뭉치에 없는 오탐은 영영 안 보인다.

⚠️ **넷 다 오탐이 나기 쉽다.** 새 법칙은 실제 은하에 걸고 양방향으로 증명한 뒤에
넣는다(`CONTRIBUTING.md` §2).
