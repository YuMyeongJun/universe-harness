# R60 — 나머지 관문도 같은 눈으로 다시 본다

## 실행 요약

R59 에서 관문 하나를 잘못 묶은 것을 찾았으니 **나머지도 같은 눈으로** 봤다.
아홉은 정말로 우주 자신의 소스를 읽는 것들이라 맞았다. 대신 **목록 밖에 있던 것**을 찾았다 —
`universe verify`(은하의 진짜 게이트: lint·build·test).

돌려 보니 **21.4초 · exit 1 · lint error 12.**
R43 에서 잰 트렁크는 **11** 이었다.

## 결과

### ⛔ R44 에서 태어난 별이 은하의 lint 를 어기고 있었다

```
src/components/pages/brandmessage/TemplateUsageCard/index.ts:1  simple-import-sort/exports
```

R45 의 컴파일 관문은 **`tsc` 만** 본다. 별은 타입은 맞는데 **그 은하의 집안 규칙**을 어겼고,
우주는 「별이 태어났다」로 끝냈다. 트렁크 error 가 11 → 12 가 됐는데 **아무도 말하지 않았다.**

### ⛔ 템플릿을 고치지 않았다

eslint 는 `export type` 을 먼저 쓰라고 한다. 그런데 그 순서는 **그 팀의 합의**다 —
`simple-import-sort` 를 안 쓰는 은하도, 다르게 설정한 은하도 있다.
**템플릿에 남의 정렬 규칙을 박으면** 다른 은하에서 반대로 틀린다.

⇒ **집안 규칙 관문**을 만들었다.
- 은하의 lint 를 **별의 폴더에만** 건다(트렁크의 기존 11건이 섞이지 않는다).
- 빨간불이고 은하가 `lintFix` 를 선언했으면 **우주가 방금 쓴 파일에만** 그것을 돌린다.
- ⛔ 남의 코드는 건드리지 않는다. 결과 파일이 없으면 **0이 아니라 「모름」**이다(§8).

실측:

```
── 집안 규칙 관문 — 은하의 lint 를 **별의 폴더에만** 건다
   ⚠️ error 1건 — 은하의 `lintFix` 를 **방금 쓴 파일에만** 돌린다.
   ✅ 별이 이 은하의 집안 규칙을 지킨다.
```

R44 의 별도 같은 방식으로 정리했고, 트렁크 lint error 는 **11로 돌아왔다**(우주가 들어오기 전 값).

## 평가

| 축 | 판정 | 근거 |
|----|------|------|
| 집행 가능성 | 통과 | 별이 태어날 때마다 돈다. 실제 은하에서 error 1건을 잡고 고치고 다시 재서 0을 확인했다 |
| 실측 기반성 | 통과 | 트렁크 11 → 별 때문에 12 → 고친 뒤 11 로 **양방향으로** 확인했다. eslint 가 원하는 순서도 짐작하지 않고 `--fix` 에게 물었다 |
| 변경 정직성 | 통과 | **템플릿을 고치지 않은 이유**를 적었다 — 그 순서는 은하의 합의이지 우주의 법이 아니다. 나머지 아홉 관문이 맞았다는 것도 그대로 적었다 |
